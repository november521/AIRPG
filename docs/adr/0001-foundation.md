# ADR 0001：模块化单体与显式依赖

日期：2026-09-26。状态：架构骨架已采用；产品未决事项仍由 PRD 管理。

## 背景

当前目标是 10 分钟切片，长期可能增长为多故事平台。多人并行容易造成跨模块直接写状态、全局单例膨胀、UI/模型/规则耦合。
工作区原先只有 PRD 和本机工具脚本；不存在需要迁移的游戏代码。

## 决策

1. Godot 工程放 `game/`，文档、脚本、工具留在工程外。防止工具依赖进入资源导入与后续导出。
2. 采用领域 / 应用 / 基础设施 / 呈现分层；每层内部按功能领域拆分；启动层单独装配。
3. 不建业务 Autoload、服务定位器或万能消息总线；使用显式 preload、构造器注入和局部信号。
4. 仅对模型、存储和随机源等真实替换点定义端口。基类默认拒绝，测试适配器不冒充生产能力。
5. 先落实单写者、版本号、原子候选提交、复制快照。完整检定/物品/RNG 事务随相应工作包实现。
6. JSON Schema 与语义检查分开；当前只支持足够用于骨架的 Schema 子集与内容目录信封。
7. 将架构依赖检查、真实引擎测试和启动测试统一为本地/CI 同一个入口。
8. 脚本长度、依赖方向等规则作为可修改的工程约束；修改需要说明真实收益并同步测试/ADR。

## 代价与限制

显式组装会多写一些构造和注入代码，但依赖可追踪。GDScript 的私有字段是约定，静态扫描也不是严格安全边界。
自带测试运行器无需外部依赖，当前适合基础行为与场景验证；未来测试量增长时可评估固定版本的专用 Godot 测试框架。
Schema 子集节省原型依赖，但不是完整标准实现。增加复杂联合类型/引用之前，应比较成熟验证库成本，避免自研验证器无限扩张。
固定引擎使 RNG 复现可检验，但升级要同时评估存档、随机算法、导出与插件兼容性。
基础层不提前实现整套剧情编辑器或通用脚本语言；扩展通过显式新版本契约实现。

## 复审触发条件

第二个正式故事、多个团队频繁修改同一目录、内容体量导致加载问题、Schema 子集需要复杂组合、独立服务器接入、性能分析确认瓶颈、引擎升级。
届时先用实际变化和测量说明问题，再决定拆模块、分块加载、引入新依赖或服务端能力。
